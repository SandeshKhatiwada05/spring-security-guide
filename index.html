    Chapter 1 · The mental model

    What is Spring Security?

    Meet the bouncer. Imagine a nightclub. It doesn't matter how good the DJ is — nobody gets in without walking past the person at the door. Spring Security is that person for your web application. Before any of your code ever runs, it decides who is allowed in and how far they can go.

    Authentication — "Who are you?"

    The bouncer checks your ID at the door. Spring checks your credentials: username, password, token, or Google account. If you can't prove who you are, you're not getting in.

    Authorization — "What can you do?"

    Once inside, your wristband decides which rooms you may enter. Spring checks your roles and permissions against the URL you requested: the VIP floor needs ADMIN, the main room just needs to be logged in.

    Client GET /account
    Bouncer Filter chain
    Who are you? What can you do?
    Controller @RestController
    Key insight

    Spring Security is just a chain of filters. Every request is intercepted before reaching your code. Your controller only ever sees requests that survived the bouncer.

    Chapter 2 · The two core jobs

    The Two Core Jobs

    Everything Spring Security does falls into one of two buckets: proving who you are, and deciding what you may do. Get these two straight and the whole framework stops feeling magical.

    Authentication

    Proving identity. Spring collects a username and password (or a JWT, or a Google token), looks the user up, and verifies the password hash. On success it stores the proven identity in the SecurityContext so every later filter and controller knows who you are. To authenticate against a database, you implement one method: 

    @Bean
UserDetailsService userDetailsService() {
    // Spring calls this on every login attempt,
    // asking "who is this username?"
    return username -> User.withUsername(username)
        .password(passwordEncoder().encode("secret"))
        .roles("USER")
        .build();
}

    Authorization

    Deciding access. Once identity is proven, Spring walks through the rules you wrote in authorizeHttpRequests and matches the requested URL against each pattern. The first match wins. If no rule matches, the default is usually "deny". Roles come from the user's authority list: 

    http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/admin/**").hasRole("ADMIN")
    .anyRequest().authenticated());

    Chapter 3 · The centerpiece

    The Filter Chain, Step by Step

    Think of the security filters as a conveyor belt. Every request is loaded onto the belt and carried through a fixed series of checks. Tap each step to follow one request from the browser all the way to your controller.

    The request arrives

    Your browser sends a plain HTTP request — a URL, headers, maybe a cookie or a token. Nothing security-related has happened yet. The request is just bytes on the wire, heading toward your server. 

    GET /user/dashboard HTTP/1.1
Host: myapp.example.com
Cookie: JSESSIONID=4A9C2E1B8F

    DelegatingFilterProxy — the front door

    Servlet containers know nothing about Spring. DelegatingFilterProxy is the bridge: a plain servlet filter that looks up your SecurityFilterChain bean and hands the request to it. This is the exact moment your request officially enters the security world. 

    // Boot registers this filter for you — no code needed.
// It finds your SecurityFilterChain bean and calls doFilter().
public class DelegatingFilterProxy extends GenericFilterBean {
    // delegates to the SecurityFilterChain in the Spring context
}

    Authentication filters — "Who are you?"

    Spring runs a series of filters, each built for one authentication mechanism. The one that matches picks your credentials and asks the AuthenticationManager to verify them. If they fail, the request dies here with a 401 — before any of your code runs. 

    // The filter that handles form-login credentials
Authentication auth = authenticationManager.authenticate(
    new UsernamePasswordAuthenticationToken(username, password));

// success -> remember the proven identity for this request
SecurityContextHolder.getContext().setAuthentication(auth);

    Authorization — "And what can you do?"

    Now Spring knows who you are, it checks what you're allowed to do. Using the rules you wrote in authorizeHttpRequests, it compares the URL against your authorities. No rule matches? The default applies — which for an unauthenticated request is a 403 or a redirect to login. 

    http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/admin/**").hasRole("ADMIN")
    .requestMatchers("/user/**").hasRole("USER")
    .anyRequest().authenticated());

    The controller — welcome in

    Only after every filter passes does your code run. By the time your @GetMapping method executes, the current user is already stored in the SecurityContext, ready to read via @AuthenticationPrincipal. 

    @RestController
public class DashboardController {

    @GetMapping("/user/dashboard")
    public String dashboard(@AuthenticationPrincipal User user) {
        return "Welcome back, " + user.getUsername();
    }
}

    Try It — simulate the bouncer

    Pretend you are the user user with role ROLE_USER. Type a URL path and watch the filter chain decide: pass, or block.

    Hardcoded rule for this demo: /public/** and /login are permitAll() · /admin/** needs ROLE_ADMIN · everything else requires an authenticated user.

    Chapter 4 · Component explorer

    The 5 Building Blocks

    Almost every Spring Security problem comes down to these five components. Click a card to see what it does, when Spring calls it, working code, and the mistake people most often make.

    What it does in plain English

    The finished, ordered list of checks every request walks through. You configure it with HttpSecurity; Spring hands the result back as a bean. Everything you will ever write in Spring Security config is really assembling this one object.

    When Spring calls it

    Built once at startup. From then on, every matching request flows through it for the lifetime of the app.

    Copy-paste ready

    @Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                .requestMatchers("/public/**").permitAll()
                .anyRequest().authenticated())
            .formLogin(Customizer.withDefaults());
        return http.build();
    }
}
    Common mistake:

    Defining two SecurityFilterChain beans whose URL patterns overlap. Order matters: the first bean whose pattern matches wins, so the most specific matchers must live in the first chain, and a chain without matchers must be last.

    What it does in plain English

    Your bridge between Spring and your user table. Spring asks it exactly one question: "given this username, give me the UserDetails." Whatever it returns — password hash, roles, account status — is everything security knows about that user.

    When Spring calls it

    During authentication, right after a filter collects the username. Also during remember-me and token refresh lookups.

    Copy-paste ready

    @Service
public class AppUserDetailsService implements UserDetailsService {

    private final UserRepository users;

    public AppUserDetailsService(UserRepository users) {
        this.users = users;
    }

    @Override
    public UserDetails loadUserByUsername(String username)
            throws UsernameNotFoundException {
        // Return null or throw: Spring treats both as bad credentials.
        return users.findByUsername(username)
                .map(MyUser::new) // your entity -> UserDetails adapter
                .orElseThrow(() -> new UsernameNotFoundException(
                        "No user named " + username));
    }
}
    Common mistake:

    Returning a UserDetails with an empty authority list. Authentication will succeed, but every authorization check fails afterwards — a confusing wall of 403s.

    What it does in plain English

    Hashes passwords so they are never stored in plain text, and verifies a typed password against a stored hash at login. The hash itself carries its encoder id (like {bcrypt}), so hashes stay portable between encoders.

    When Spring calls it

    encode() on registration and password changes. matches() on every login.

    Copy-paste ready

    @Bean
public PasswordEncoder passwordEncoder() {
    // Strength 12 makes brute-force painfully slow (one-time cost).
    return new BCryptPasswordEncoder(12);
}

// at registration:
String hash = passwordEncoder().encode(rawPassword);

// at login, Spring calls this for you:
boolean ok = passwordEncoder().matches(rawPassword, storedHash);
    Common mistake:

    Defining no PasswordEncoder bean. Spring then requires stored passwords to carry a {noop} prefix — which literally means "store and compare in plain text." Never ship that.

    What it does in plain English

    The conductor. It holds a list of AuthenticationProvider objects and tries each one until an authentication succeeds — or gives up and throws. Filters treat it as a black box that answers one question: are these credentials real?

    When Spring calls it

    Every time a login attempt needs verifying — used by the username/password filter, the JWT filter, and the OAuth2 filter alike.

    Copy-paste ready

    @Bean
public AuthenticationManager authenticationManager(
        AuthenticationConfiguration configuration) throws Exception {
    // Spring wires the default providers for you.
    return configuration.getAuthenticationManager();
}
    Common mistake:

    Building it by hand with a bare DaoAuthenticationProvider, then wondering why your UserDetailsService is never consulted. Use AuthenticationConfiguration unless you genuinely need custom providers.

    What it does in plain English

    A storage box holding the Authentication of the current request. Each thread keeps its own copy, so you can read "who is logged in" anywhere without passing the user around as a parameter.

    When Spring calls it

    Filled right after a successful authentication, and cleared after the request finishes. You read it in controllers, services, and templates.

    Copy-paste ready

    Authentication auth = SecurityContextHolder.getContext()
        .getAuthentication();

String name = auth.getName();
for (GrantedAuthority authority : auth.getAuthorities()) {
    // e.g. "ROLE_ADMIN"
    System.out.println(authority.getAuthority());
}
    Common mistake:

    Reading the context before authentication has run (for example in a filter that runs earlier than the security chain), or stashing non-serializable objects inside it.

    Chapter 5 · Put it together

    A Complete, Runnable Example

    The full SecurityConfig.java below is valid Spring Security 6 using the lambda DSL. It secures some paths, leaves others public, enables form login with a custom page, and registers two in-memory users with BCrypt-hashed passwords. The numbered callouts after the code explain each piece. 

    package com.example.demo;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    // (1) This bean IS your security setup, top to bottom.
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/public/**", "/login", "/error").permitAll() // (2)
                .requestMatchers("/admin/**").hasRole("ADMIN")                 // (3)
                .requestMatchers("/user/**").hasRole("USER")                   // (3)
                .anyRequest().authenticated())                                 // (4)
            .formLogin(form -> form
                .loginPage("/login")                                           // (5)
                .defaultSuccessUrl("/user/dashboard", true)
                .permitAll())
            .logout(logout -> logout.logoutSuccessUrl("/login?logout"));

        return http.build();
    }

    // (6) Demo users, hashed with BCrypt — never {noop}.
    @Bean
    public UserDetailsService users(PasswordEncoder encoder) {
        UserDetails admin = User.withUsername("admin")
                .password(encoder.encode("admin123"))
                .roles("ADMIN")
                .build();

        UserDetails user = User.withUsername("user")
                .password(encoder.encode("user123"))
                .roles("USER")
                .build();

        return new InMemoryUserDetailsManager(admin, user);
    }

    // (7) One encoder for the whole app.
    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}

    @EnableWebSecurity turns on Spring Security's configuration support. You will see this on every security config class.

    filterChain(HttpSecurity http) is where all the rules live. The method returns a SecurityFilterChain bean that Spring uses as the blueprint for the filter chain. Nothing runs yet — this is just the plan.

    The public paths. /public/**, /login, and /error are explicitly marked permitAll() — no authentication required. Everything you forget to list here is locked down by the next rule.

    Role-gated neighborhoods. /admin/** demands the ADMIN role; /user/** demands USER. An authenticated user with the wrong role gets a 403.

    anyRequest().authenticated() is the safety net: any URL not matched above still requires a logged-in user. This "default-deny" stance is what makes the config safe.

    Form login enables the standard login form, points it at your custom page (/login), and sends successful logins to the dashboard. Logout returns users to the login page.

    In-memory users let you test immediately. The passwords are encoded with BCrypt at startup — the plain values you type never live in memory as plain text. Swap this bean for a database-backed service in a real app.

    The one dependency

    Add this to pom.xml. The Spring Boot parent manages the version, so no version tag is needed. Once it is on the classpath, Spring Security auto-configures itself with a default login form and generated password — then your SecurityConfig takes over. 

    <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>

    Chapter 6 · Pitfalls

    Common Beginner Mistakes

    Every one of these has cost someone an afternoon. They all have the same shape: the app runs, but something quietly fails. Knowing them in advance saves the debugging.

    Missing PasswordEncoder bean

    You registered users with .password("plain123"). Without an encoder bean, Spring only understands {noop}-prefixed values, so the app runs — but passwords are stored and compared in plain text.

    Why it happens

    Spring's default behavior kicks in when you never define an encoder, and "it worked" in a tutorial because the tutorial used {noop} too.

    The fix

    @Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
// then encode real passwords:
// .password(passwordEncoder().encode("plain123"))

    hasRole vs hasAuthority confusion

    hasAuthority("ADMIN") checks the exact string "ADMIN", while hasRole("ADMIN") first prepends ROLE_ and checks "ROLE_ADMIN". Mixing them up silently locks users out.

    Why it happens

    The two methods look interchangeable, and many older examples switch between them without explanation.

    The fix

    // when the authority is stored as ROLE_ADMIN:
.requestMatchers("/admin/**").hasRole("ADMIN"); // prepends ROLE_

// is the same as:
.requestMatchers("/admin/**").hasAuthority("ROLE_ADMIN");

    Disabling CSRF blindly for REST

    Copy-pasting .csrf(csrf -> csrf.disable()) "to make it work" leaves cookie-based apps open to cross-site request forgery. A browser can be tricked into sending your cookies to your own API.

    Why it happens

    A JWT tutorial said "turn CSRF off," and the same line landed in a session-based app.

    The fix

    // stateless REST API only (no cookies) — acceptable:
http.csrf(csrf -> csrf.disable());

// cookie/session web app — keep CSRF on (the default).

    Forgetting the ROLE_ prefix

    When using hasAuthority you must include the full authority string. If your user has role ROLE_ADMIN and you check hasAuthority("ADMIN"), it never matches — even though the login succeeded.

    Why it happens

    The prefix is invisible in logs and typical debugging output, so it is easy to miss.

    The fix

    .requestMatchers("/admin/**").hasAuthority("ROLE_ADMIN");
// or use hasRole("ADMIN") — the prefix is added for you

    403 vs 401 confusion

    They look similar but mean different things. 401 means "you are not authenticated at all." 403 means "we know who you are, but you lack permission." Beginners debug a 403 by trying to log in "harder."

    Why it happens

    Both responses look identical in a browser and are lumped together in casual speech as "access denied."

    The fix

    // 401 -> not authenticated. Show the login page / send a token.
// 403 -> authenticated but not allowed. Fix the roles or rules.

    UserDetails with no authorities

    If loadUserByUsername builds a user without authorities, authentication succeeds but every authorization check fails — everything returns 403.

    Why it happens

    You mapped the username and password hash but forgot to map the role column.

    The fix

    // always attach authorities from your entity:
return new User(entity.getUsername(), entity.getPassword(),
    List.of(new SimpleGrantedAuthority(entity.getRole())));

    Chapter 7 · Choose your approach

    When to Use What

    Spring Security offers several authentication styles because apps are built differently. Start from your architecture, not from a favorite library.

    Recommended Spring Security approach for common application scenarios
    Scenario Recommended approach
    Server-rendered web app with Thymeleaf Form login + sessions
    REST API for React / Vue / Angular JWT + stateless
    "Login with Google" OAuth2 Client
    Enterprise SSO OAuth2 / SAML
    Microservices internal calls Mutual TLS or API keys

    Chapter 8 · Quick reference

    Quick Reference Cheat Sheet

    The four facts you will reach for most. Tap to expand.

    @EnableWebSecurity activates security configuration support.

    @PreAuthorize runs a SpEL rule at the method level — the most expressive option for fine-grained checks.

    @Secured is the older, simpler method-level rule using plain role names.

    @EnableWebSecurity                        // activates security config
@PreAuthorize("hasRole('ADMIN')")         // method-level, most flexible
@Secured("ADMIN")                         // method-level, simple & legacy

    SecurityFilterChain — the pipeline your requests flow through. You build it with HttpSecurity and expose it as a bean.

    HttpSecurity — the fluent builder that assembles that pipeline.

    AuthenticationManager — verifies credentials by trying its registered providers.

    SecurityFilterChain      // the pipeline requests flow through
HttpSecurity             // builder that assembles that pipeline
AuthenticationManager    // verifies credentials via providers

    401 Unauthorized — you are not authenticated. The app does not know who you are. Fix: log in, or send a valid token.

    403 Forbidden — you are authenticated but not allowed to access this URL. Fix: grant the right role or authority.

    200 OK — you passed the bouncer and reached the controller.

    BCrypt (recommended) — slow by design, salt built into the hash, the de facto standard. Use it unless you have a strong reason not to.

    Argon2 — memory-hard and modern, more tuning parameters, a great choice for new high-security apps.

    PBKDF2 — older and NIST-endorsed, built into the JDK, but weaker against GPU-based attacks than the two above.

    // pick one and register it once as a bean
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
